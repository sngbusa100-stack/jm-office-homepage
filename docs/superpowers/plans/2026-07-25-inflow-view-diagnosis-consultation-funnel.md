## 1. 이번 계획에서 해결할 문제

현재 시스템에는 메인 업무분야 6개 페이지, 메인 셀프 진단 3종, 비자 상세 6개 페이지와 진단 6종, 중앙 상담 접수 API 및 행정심판 연동기가 존재한다.

그러나 방문자 관점에서는 다음 연결이 충분히 명확하지 않다.

1. 검색·블로그·SNS에서 어떤 페이지로 들어와야 하는지
2. 상세 페이지에서 무엇을 확인할 수 있는지
3. 설명을 읽은 뒤 어떤 진단을 해야 하는지
4. 진단 결과가 상담 신청에 어떻게 이어지는지
5. 상담 접수 뒤 어떤 업무가 자동으로 준비되는지
6. 각 단계에서 얼마나 이탈하고 전환되는지

따라서 이번 작업은 페이지 수를 무조건 늘리는 것이 아니라, 기존 페이지를 아래 전환 흐름에 맞게 재구성한다.

```text
유입
→ 문제·분야별 설명/조회 페이지
→ 필요 시 셀프 진단
→ 개인화 결과
→ 상담 선택/신청
→ 접수·분야 라우팅
→ 행정사 검토·사건 전환
→ 자동 진단·자료요청·문서 초안
```

## 2. 핵심 설계 원칙

### 2.1 하나의 기본 흐름과 세 가지 진입 방식

기본 흐름은 `유입 → 조회 → 진단 → 상담`으로 하되 방문자의 긴급도에 따라 세 가지 길을 제공한다.

#### 정보 탐색형

```text
검색/콘텐츠 → 분야 설명 → 기준·절차·서류 조회 → 진단 → 상담
```

#### 고의도형

```text
검색광고/직접 링크 → 해당 분야 랜딩 → 진단 바로 시작 → 상담
```

#### 긴급형

```text
처분·기한 임박 → 기한 경고 확인 → 진단을 생략하고 긴급상담 또는 공식기관 확인
```

진단은 권장 경로이지 강제 관문이 아니다. 기한이 임박한 방문자는 즉시 상담이나 공식 확인으로 갈 수 있어야 한다.

### 2.2 ‘조회’의 정의

이번 계획에서 조회는 또 하나의 복잡한 설문을 의미하지 않는다.

- 내가 이 업무의 대상인지
- 가장 먼저 확인할 기한이 있는지
- 어떤 서류가 필요한지
- 공식적으로 어디에서 확인해야 하는지
- 혼자 진행할 수 있는 단계와 행정사 검토가 필요한 단계가 무엇인지

를 상세 페이지에서 빠르게 확인하는 단계다.

### 2.3 하나의 브랜드 경험, 분리된 전문 엔진

- 방문자에게는 메인과 비자 사이트가 같은 정명 시스템으로 보이게 한다.
- 코드 저장소와 배포는 현재처럼 분리 유지한다.
- 공통 로고, 색상, 용어, 진행단계, CTA 문구, 면책 원칙을 통일한다.
- 비자 진단은 비자 엔진이 담당하고, 행정심판 사건 자동화는 로컬 행정심판 엔진이 담당한다.
- 모든 상담 접수는 중앙 접수번호를 사용한다.

### 2.4 자동 생성과 사람 검토의 경계

- 진단 직후: 고객용 준비도·긴급도·부족서류 안내
- 상담 접수 직후: 행정사용 접수요약·누락정보·추가질문 초안
- 사건 전환 후: 기한·증거·내부진단·문서 초안
- 발송·제출 전: 행정사 최종 검토 필수

상담 접수만으로 최종 제출 문서를 자동 확정하지 않는다.

## 4. 공통 설명·조회 랜딩 템플릿

각 분야 페이지는 다음 순서를 공통으로 사용한다.

1. **검색어와 일치하는 제목**
   - 예: `음주운전 면허취소 통지를 받았다면 먼저 확인할 사항`
   - 예: `2026년 E-7 비자 임금·직종·고용요건 사전 확인`
2. **한 줄 상황 안내**
   - 누구에게 필요한 페이지인지 즉시 설명
3. **즉시 행동 CTA**
   - `3분 사전진단`
   - `기한이 임박했다면 바로 상담`
4. **이 페이지에서 확인할 수 있는 것**
   - 대상, 기한, 요건, 준비서류, 다음 행동
5. **핵심 기준·기한 조회**
   - 법령·공식 출처·기준 확인일 포함
6. **필요서류 체크리스트**
7. **진행 절차**
8. **혼자 진행할 수 있는 부분 / 검토가 필요한 부분**
9. **자주 묻는 질문**
10. **진단 CTA 반복**
11. **상담 절차와 예상 회신 방식**
12. **면책·공식기관 확인 안내**

페이지 상단에서 진단을 시작할 수 있게 하되, 설명을 먼저 읽고 싶은 방문자도 방해받지 않게 한다.

## 5. 분야별 1차 콘텐츠 범위

### 5.1 음주운전 면허 구제

- 처분 통지 여부
- 이의신청·행정심판 기한
- 집행정지와 효력 관계
- 과거 위반 이력
- 생계상 운전 필요성
- 준비서류와 정상참작 자료
- `/check/dui` 연결

### 5.2 영업정지·행정심판

- 사전통지 단계와 처분 확정 단계 구분
- 의견제출 기한
- 행정심판 청구기간
- 집행정지 검토 필요성
- 업종·처분 사유별 추가 확인 필요
- 매출·생계·CCTV 등 증거자료
- `/check/suspension` 연결

### 5.3 국가보훈

- 최초 등록과 비해당 결정 불복 구분
- 공무 관련성 입증
- 군·민간 의무기록
- 오래된 기록 확보 경로
- 재신청·재심의·행정심판 구분
- `/check/veterans` 연결

### 5.4 인허가

- 인허가 종류를 모르는 방문자용 분류
- 입지·시설·결격·자격 요건
- 반려와 보완 요구의 차이
- 사업계획서·정관·시설자료 등 준비서류
- 1차에는 상담 연결, 실제 문의 데이터를 본 뒤 간이 진단 추가 여부 결정

### 5.5 토지보상·내용증명·계약서

- 세 업무를 한 페이지에서 무리하게 섞지 않도록 내부 섹션과 직접 링크를 분리
- 토지보상: 협의·감정평가·재결 절차
- 내용증명: 증명되는 것과 강제되지 않는 것
- 계약서: 체결 전 검토 항목
- 1차에는 상담 연결, 문의량에 따라 별도 랜딩 분화

### 5.6 비자 6종

- 비자별 대상자
- 핵심 요건
- 연도별로 변하는 기준
- 준비서류
- 공식 출처와 확인일
- 현재 체류자격·기한에 따른 주의
- 해당 `/diagnosis/:slug` 연결
- 결과에서 중앙 상담 접수로 직접 전달

## 7. 전환 측정 설계

## 7.1 측정 이벤트

| 이벤트 | 의미 |
|---|---|
| `landing_view` | 분야 설명·조회 페이지 도달 |
| `landing_cta_click` | 진단 또는 상담 CTA 클릭 |
| `diagnosis_start` | 진단 첫 답변 시작 |
| `diagnosis_complete` | 결과 화면 도달 |
| `consult_view` | 상담 화면 도달 |
| `consult_submit` | 상담 접수 성공 |
| `qualified` | 행정사가 적격 문의로 판단 |
| `retained` | 실제 수임 전환 |
| `work_completed` | 업무 완료 |

## 7.2 이벤트에 넣을 수 있는 값

- 익명 세션/여정 ID
- 페이지 유형
- 분야 코드
- 유입 출처
- `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`
- 언어
- 이벤트 시각

## 7.3 이벤트에 넣지 않는 값

- 성명·전화번호·이메일
- 진단 답변 원문
- 구체적인 처분 내용
- 여권번호·외국인등록번호
- 상담 내용

상담 접수 데이터와 익명 전환 통계는 논리적으로 분리한다. 진단 상세는 사용자가 상담 접수에 명시적으로 동의한 경우에만 접수 레코드에 포함한다.

## 7.4 측정 방식

1차 구현은 분석 도구에 종속되지 않는 공통 `trackFunnelEvent` 계층을 만든다.

- 사이트 코드에서는 공통 함수만 호출
- 개발·테스트에서는 메모리 스텁
- 운영에서는 개인정보 없는 1차 측정 엔드포인트 또는 승인된 분석 도구로 전송
- 운영 전 개인정보처리방침과 동의 필요 여부를 검토

이 구조로 만들면 향후 GA4 또는 다른 분석 도구로 바꾸더라도 각 페이지 코드를 다시 수정하지 않아도 된다.

## 8. 비자 진단→중앙 상담 안전 전달

현재 비자 결과는 중앙 상담 URL로만 이동하므로 진단 상세가 소실된다. 이를 다음 방식으로 보완한다.

1. 비자 결과 화면에서 `상담에 진단 결과 포함` 여부를 명시적으로 선택
2. 동의한 경우에만 비자 종류·질문 ID·선택지 ID·결과 레벨을 서버로 전달
3. 버전된 `visaDiagnosis` 스키마 사용
4. 서버가 비자·문항·선택지를 다시 검증하고 결과 레벨을 재계산
5. 일회성 `handoffToken` 또는 접수용 `submissionId` 발급
6. 중앙 상담 화면은 토큰으로 안전하게 결과를 불러와 분야와 상담 내용을 미리 채움
7. URL에는 답변 원문·연락처·상담 내용을 넣지 않음
8. 상담 접수 완료 후 브라우저 세션의 진단·토큰 정리

개업 전에는 서버 접수 기능을 열지 않고 UI·검증 테스트까지만 수행한다.

## 9. 검색 노출 설계

## 9.1 메인 홈페이지

- 기존 sitemap·canonical·경로별 메타데이터 유지
- 서비스 페이지별 제목·설명을 검색의도 중심으로 개선
- 주요 설명 랜딩은 빌드 시 HTML 사전 렌더링을 검토
- 진단 결과·상담 완료·관리자 페이지는 `noindex`

## 9.2 비자 홈페이지

- `robots.txt`, `sitemap.xml` 추가
- 비자별 canonical과 제목·설명 추가
- 5개 언어 URL 전략 확정 후 `hreflang` 적용
- 같은 한국어 내용을 기계번역으로 대량 복제하지 않음
- E-7·F-6부터 사전 렌더링 우선
- 결과·상담 완료 페이지는 `noindex`

## 9.3 링크 전략

- 블로그·SNS 링크는 일반 홈이 아니라 관련 랜딩으로 연결
- 예:
  - 음주운전 콘텐츠 → `/services/dui`
  - 영업정지 콘텐츠 → `/services/suspension`
  - E-7 콘텐츠 → 비자 `/visa/e7`
- 모든 외부 콘텐츠 링크에 UTM을 붙이되 개인정보는 넣지 않음

- E-7·F-6는 비자 사이트의 핵심 유형이고, 진단 결과 전달이 완성되면 비자 업무 확장 패턴을 만들 수 있다.
- 나머지 분야는 실제 유입·상담 데이터를 본 뒤 진단 개발 여부를 결정한다.

## 12. 완료 기준

다음 조건을 모두 충족해야 이번 고도화가 완료된 것으로 본다.

1. 주요 유입 링크가 일반 홈이 아니라 관련 분야 랜딩으로 연결된다.
2. 랜딩에서 대상·기한·요건·서류·절차를 확인할 수 있다.
3. 진단이 있는 분야는 설명 페이지에서 해당 진단으로 직접 이동한다.
4. 긴급 방문자는 진단을 생략하고 상담·공식기관 확인으로 이동할 수 있다.
5. 진단 결과가 상담에 안전하게 포함된다.
6. 비자 결과도 동의 후 중앙 접수에 전달된다.
7. 유입·조회·진단·상담·수임 단계의 전환율을 확인할 수 있다.
8. 분석 이벤트에 개인정보와 진단답변이 포함되지 않는다.
9. 상담 접수는 분야별 내부 처리 시스템으로 라우팅된다.
10. 고객 발송·최종 제출 전 행정사 검토가 강제된다.
11. 자동 테스트, 모바일·데스크톱 브라우저 검증, 리뷰 에이전트 검토를 통과한다.
