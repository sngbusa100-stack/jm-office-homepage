- 배경: 방문자가 자기 문제를 설명으로 확인하기 전에 진단부터 만나는 구조. 홈에서 셀프 진단 섹션이 업무 분야 섹션보다 위에 있고(`HomePage.tsx`), 상단 메뉴가 `업무분야`와 `셀프 진단`을 동급으로 나열해(`Navbar.tsx`) "설명 다음이 진단"이라는 순서 정보가 어디에도 없다. 또한 업무 분야 6개 중 진단이 있는 것은 3개뿐이라 나머지 분야 방문자는 다음 행동이 끊긴다.

## 구조

```
홈 (문제 인식)
  → 업무 분야 목록 (내 문제 찾기)
    → 분야 상세 = 한 페이지 안의 4단계
        1 설명        절차·기한·대상
        2 요건·서류 조회
        3 내 상황 진단  내부 진단 4 · 외부 진단 1(비자) · 확인 목록 1(문서)
        4 상담 준비
      → 상담 접수

비자만 3단계에서 다국어 진단센터로 이동 후 중앙 상담(centralConsultUrl)으로 복귀
분야를 모르는 방문자용 /check 선택 페이지는 유지하되 상단 메뉴에서 제외
```

## 결정 사항

1. **분야 하나 = 페이지 하나 = 흐름 하나.** 진단을 분야에서 떼어내지 않는다. 상단 메뉴에서 `셀프 진단`을 내리고 분야 상세 안의 3단계로 편입한다. `/check` 라우트 자체는 유지하되 홈·상담 페이지에서만 링크한다(분야를 모르는 방문자용 진입점).

2. **인허가 진단만 신설한다.** `CheckDomain`에 `permit`을 추가하고 `data/checks/permit.ts`를 만든다. 인허가는 요건·관할이 갈려 진단 가치가 크고, 문서 분야(토지보상·내용증명·계약서)는 문항화가 어렵다.

3. **문서 분야는 진단 대신 확인 목록.** 이미 `services.ts`에 있는 `selfService` 항목을 3단계 자리에 "상담 전 확인 목록"으로 배치한다. 새 콘텐츠를 만들지 않으므로 법률 문구 검수 부담이 없다.

4. **인허가 진단 문구는 검수 게이트를 둔다.** `services.ts`의 기존 콘텐츠는 주인님 계획서 원문을 한 글자도 고치지 않고 사용한 것으로 기록돼 있다(`memory.md`). 인허가 진단은 새로 쓰는 콘텐츠이므로 **초안 작성 → 주인님 검수 → 배포** 순서를 지킨다. 근거 법령은 국가법령정보센터 원문을 확인해 조문을 붙이고 확인일을 남긴다.

5. **비자 사이트는 별도 유지하고 시각만 통일한다.** 5개 언어 × 비자 6종 구조를 메인에 흡수하면 다국어 라우팅·번역 데이터 이관과 기존 배포·연동을 다시 손봐야 한다. 대신 헤더·색·4단계 문구를 메인과 맞추고, 이동 버튼에 "다국어 진단센터로 이동합니다"를 명시해 이탈로 느껴지지 않게 한다. 복귀 경로(`centralConsultUrl`)는 이미 구현돼 있다.

6. **4단계 문구는 두 사이트가 글자 단위로 같아야 한다.** 비자 사이트 `flowSteps`의 한국어 문구(`비자 설명` → 메인은 `설명`, `요건·서류 조회`, `내 상황 진단`, `상담 준비`)를 기준으로 맞추고, 불일치를 막는 테스트를 둔다.

7. **구조와 디자인을 두 단계로 나눠 배포한다.** Phase 1(구조)을 먼저 배포해 효과를 확인하고, 승인 후 Phase 2(디자인)를 진행한다. 한 번에 바꾸면 회귀 원인을 가릴 수 있다.

## Phase 1 — 구조

### 인허가 진단 문항 (초안 10문항 — 주인님 검수 필요)

기존 `CheckDefinition` / `Question` / `QuestionOption` 구조와 4단계 레벨(`urgent` · `documents` · `official` · `ready`)을 그대로 쓴다. 결과 화면·상담 전달 로직은 수정 없이 재사용된다.

| # | 문항 | 주요 레벨 |
|---|---|---|
| 1 | 필요한 인허가 종류 (법인설립·공장등록·영업허가·기타) | ready / official |
| 2 | 현재 단계 (검토·서류준비·신청함·보완요구·반려) | official / urgent |
| 3 | 관할 기관 확인 여부 | official |
| 4 | 사업장 입지·용도지역 확인 여부 | official / documents |
| 5 | 시설·장비 기준 확인 여부 | documents |
| 6 | 인력·자격 요건 해당 여부 | documents |
| 7 | 대표자·법인 결격사유 확인 여부 | official |
| 8 | 보완 요구 기한 | urgent |
| 9 | 반려 이력과 사유 확보 여부 | documents / official |
| 10 | 사업 개시 예정일까지 남은 기간 | urgent / ready |

기한 압박(8·10번)이 `urgent`로 분류되어 기존 음주운전·영업정지 진단과 결과 화면이 그대로 호환된다.

### 화면 변경

- `HomePage.tsx` — 업무 분야 섹션을 진단 섹션 위로 이동. 히어로 주 버튼을 `업무 분야 살펴보기`로, 진단은 보조 버튼으로 유지(기한이 급한 방문자용 탈출구). 진단 섹션 문구를 "분야를 모르겠다면" 성격으로 조정.
- `Navbar.tsx` — 메뉴 4개 → 2개(`행정사가 필요한 이유` · `업무분야`) + 우측 상시 `상담 문의` 버튼. `셀프 진단`은 분야 안으로 편입하고, `상담 안내`는 상담 버튼과 목적지가 같아 중복을 없앤다.
- `ServiceFlowSteps.tsx` (신설) — 분야 상세 상단 4단계 표시, 현재 단계 강조. 비자 분야는 3단계에 외부 이동 표기.
- `ServicePage.tsx` — 스텝 표시 배치, 진단 없는 분야의 3단계 자리에 확인 목록 배치, 비자 외부 이동 안내 문구.

## Phase 2 — 디자인·가독성

측정 근거와 대응:

1. **본문 줄 길이** — 분야 상세가 `page-shell`(max-width 1120px, `app.css:22`)을 쓰는데 `.service-landing`에는 폭 제한 스타일이 없다. 본문 문단이 1072px로 깔려 한 줄에 한글 90자 이상이 된다. → 본문 컨테이너 **780px**(한글 45~50자/줄), 카드 그리드·스텝 표시만 전체 폭.
2. **섹션 위계 부재** — `ServicePage`가 헤더 + 섹션 9개를 같은 `h2`, 같은 간격(52px, `app.css:186`)으로 나열해 법정 기한이 다른 섹션과 동급으로 보인다. → 3단 위계: ① 법정 기한 = 상단 강조 카드, ② 절차·서류 = 일반 섹션, ③ 공식 출처·FAQ = 기본 접힘.
3. **타이포 토큰 부재** — `tokens.css`에는 색·반경·그림자만 있고 타이포 토큰이 없다. `app.css`에 고정 폰트 크기가 15종(0.75~1.6rem) 산재한다. → `--fs-*` · `--lh-*` 신설 후 4단계로 축소.
4. **본문 기본 크기** — `body`에 font-size 지정이 없어 브라우저 기본 16px. 주 이용층이 통지서를 들고 급하게 보는 상황임을 고려해 **17px / 줄간격 1.75**.
5. **태블릿 구간 없음** — `.grid-3` · `.grid-2`가 768px에서 곧바로 1열(`app.css:47`). → 1024px에 2열 단계 추가.
6. **CTA 중복** — `ServiceActions`가 상단(`ServicePage.tsx:82`)·하단(`ServicePage.tsx:186`) 두 번, 각 2개씩 = 같은 버튼 4개. → 상단 1개(주 행동), 하단 2개.
7. **모바일 하단 고정 CTA** — 긴 상세 페이지에서도 다음 단계가 항상 보이도록. 기존 버튼 최소 높이 48px와 일관되게.

유지할 것: `designTokens.test.ts`의 강조색 대비 AA 검사, 버튼 최소 높이 48px, `word-break: keep-all`, `prefers-reduced-motion` 대응. `--text-soft`(대비 3.5:1)는 비활성 입력칸 전용이라 접근성 위반이 아니므로 그대로 둔다.
