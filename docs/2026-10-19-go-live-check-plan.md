# ⑥ 개업 전환 점검 — 계획 (2026-10-19, 주인님 승인: 추천안, 카카오 채널은 개업 필수 유지, 비자 사이트 문구는 별도 과제)

방향 문서 `docs/2026-10-19-function-direction.md` 5절의 마지막 순서다(보고서 16번). 개업하는 날 스위치 하나라도 빠뜨리면 두 가지 일이 생긴다. 접수가 열리지 않거나, 반대로 업무신고 전에 접수가 열려 상담 행위가 된다(행정사법 제10조·제36조②1). 이 계획은 개업 스위치를 한 번에 점검하고, 홈페이지 문구가 스위치 하나로 함께 바뀌게 하는 것이 목적이다.

## 2. 설계

### 2-1. 점검 스크립트 `npm run go-live:check` (읽기 전용)
- 파일·설정을 바꾸지 않는다. 항목마다 ✅ / ❌ / ⚠️(사람 확인)를 출력한다.
- **지금(개업 전)** 돌리면 "개업 전에 채울 것" 목록이 나온다. **개업 뒤** 돌리면 "개업 상태가 완전히 맞는지"를 판정한다.
- `--strict`로 돌리면 ❌가 하나라도 있을 때 종료코드 1을 낸다.
- 점검 항목
  1. **사무소 정보**: isOpen, 필수값(REQUIRED_WHEN_OPEN과 같은 목록), 등록번호 형식
  2. **방침**: 시행일과 동의 버전이 같은지. 개업일(`office.json`에 새로 넣는 `openedOn`)보다 시행일이 앞서면 ❌
     - 개업하면 방침 안의 개업 전 문장이 바뀐다. 그러면 방침 변경이 되므로 시행일·변경 이력을 갱신해야 한다.
  3. **문구**: isOpen인데 화면 소스·빌드 결과(dist)에 개업 전 문구('개업 준비 중' 등)가 남아 있으면 ❌
  4. **운영 API**(네트워크)
     - `/api/consult`에 빈 요청을 보내 응답을 본다. 503 not_accepting이면 닫힘, 400이면 열림이다.
       - 빈 요청은 검증 단계에서 거절되므로 접수 레코드는 생기지 않는다. 요청 제한 1회만 쓴다.
     - isOpen과 접수 상태가 어긋나면 ❌다. 예: isOpen=false인데 열림 → **업무신고 전 접수 위험**.
     - `/api/connector`·`/api/cron-purge`가 인증 없이 401인지 본다.
  5. **운영 비밀값**: `vercel env ls production`으로 이름만 확인한다(값은 읽지 않음).
  6. **운영 화면**: jungmyungoffice.com 첫 화면에 등록번호가 보이는지, 개업 전 띠가 사라졌는지 확인한다(개업 뒤).
  7. **로컬 연동**: 로컬 `.env`에 CONNECTOR_* 키가 있는지(값은 출력 안 함), 작업 스케줄러 마지막 결과가 0이고 1시간 안에 돌았는지 본다(Windows에서만).
  8. **비자 사이트**: 개업 뒤인데 운영 화면에 개업 전 문구가 남아 있으면 ❌
  9. **사람이 할 일(⚠️ 목록)**: 업무신고 수리증, 행정사회 가입, 사업자등록, 카카오 채널, 네이버·구글 재수집, 카카오 공유 캐시, 명함·블로그 표기, 시험 접수 1건 왕복
- 네트워크·CLI 호출은 주입식으로 짜서 테스트에서 흉내 낸다. 판정 함수는 순수 함수로 두고 vitest로 고정한다.

### 2-2. 홈페이지 개업 문구를 isOpen 하나로 전환 (추천)
- 지금은 `isOpen`만 바꿔도 첫 화면 띠·FAQ·방침·면책 문구가 "개업 준비 중"으로 남는다. 이 문구들을 `office.isOpen` 기준으로 바꿔 보여 준다(상담 화면과 같은 방식).
- 개업 후 문구는 새 사실을 만들지 않는다. 예: FAQ는 "상담은 아래 상담 신청 또는 사무실 전화로 받습니다". 문구 초안은 구현 때 주인님께 보여 드리고 확인받는다.
- 방침의 개업 전 문장이 바뀌는 것은 방침 변경이다. 그래서 개업일에 시행일·`CONSENT_VERSION`·변경 이력 한 줄("개업에 따른 상담 접수 개시")을 함께 바꾼다. 점검 스크립트 2번이 이를 확인한다.
- 테스트: isOpen true/false 두 상태로 각 화면을 렌더링해 문구를 고정한다. 사전 렌더링 결과(dist)도 검사한다.

### 2-3. 개업일 순서 (문서로만, `docs/go-live-runbook.md`)
1. 사람: 업무신고 수리·행정사회 가입·사업자등록을 마친다.
2. 개업 커밋
   - `office.json`: 등록번호·사업자번호·openedOn을 넣고 isOpen=true
   - 방침 시행일·동의 버전·변경 이력 갱신
   - `npm run go-live:check`: 로컬 항목 ✅, 운영 API는 아직 닫힘이라 ❌가 정상
3. 배포 승인 → master 푸시
4. Vercel `CONSULT_OPEN=true`(주인님 승인 뒤 CLI로 설정) → 다시 배포
5. `npm run go-live:check --strict`: 모두 ✅
6. 시험 접수 1건을 넣는다.
   - Telegram 알림 → 로컬 대기함 적재(30분 안) → 회신 초안 → 종결 순서로 확인
   - 시험 건을 파기한다.
7. 네이버·구글 재수집, 카카오 캐시 초기화(주인님)

## 3. 하지 않는 것
- 스크립트가 isOpen·CONSULT_OPEN을 직접 바꾸는 일. 개업은 사람이 결정하고 승인한다.
- 비자 사이트의 개업 후 문구 작성(5개 언어, 번역 검수 필요). 이번에는 점검 항목으로만 넣고, 문구 전환은 별도 과제로 한다.
- 업무신고 수리 여부의 자동 확인(공개 API 없음)

## 4. 순서 (TDD)
1. 판정 함수 테스트 → `scripts/go-live-check.mjs`(+ `lib`), `package.json`에 `go-live:check`
2. 화면 문구 전환 테스트(isOpen 두 상태) → 구현. 개업 후 문구 초안을 주인님께 확인
3. `office.json`에 `openedOn: null`을 추가하고 `Office` 타입·verify-office를 맞춤
4. 타입 검사·전체 테스트·빌드·verify-dist·리뷰 에이전트
5. 지금 상태로 스크립트를 실제 실행해 결과(개업 전 할 일 목록)를 보고
6. 커밋. 배포는 승인 뒤. 화면 문구는 isOpen=false에서 바뀌지 않으므로 배포해도 보이는 변화가 없어야 한다(테스트로 확인)

작업량은 S~M이다. 홈페이지 저장소만 고친다.

## 5. 주인님께 여쭐 것
1. **범위**: 점검 스크립트 + 홈페이지 개업 문구 자동 전환(추천)으로 할지, 점검 스크립트만 할지 정해 주십시오.
2. **카카오 채널**: 지금은 개업 필수값이라 채널이 없으면 개업 전환이 막힙니다. 개업 전에 채널을 만드실지, 필수에서 뺄지 정해 주십시오.
3. **비자 사이트 개업 후 문구**(5개 언어): 별도 과제로 미룰지(추천) 정해 주십시오.
