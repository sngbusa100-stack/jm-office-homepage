# ③ 매일 아침 Telegram 운영 요약 — 계획 (2026-10-19, 주인님 승인: 추천안, PC 24시간 가동)

방향 문서 `docs/2026-10-19-function-direction.md` 5절의 두 번째 순서다. 목적은 조용한 실패를 막는 것이다. 대시보드를 열지 않아도 사무소 휴대폰에 매일 아침 한 번 접수·연동·파기 상태가 뜨게 한다.

## 1. 현황 (코드 확인 결과)

- 홈페이지에는 이미 매일 도는 cron이 하나 있다. `api/cron-purge.js`, `vercel.json` 일정 `0 18 * * *`(UTC, 한국 03시)이고, 120일이 지난 완료 건을 파기한다. 그러나 결과를 어디에도 남기지 않는다. 실패해도 응답 코드 502만 남고 아무도 보지 않는다.
- Telegram 발송은 `api/consult.js`에만 있다. 환경변수는 `TELEGRAM_BOT_TOKEN`·`TELEGRAM_CHAT_ID`(접수 알림과 같은 대화방)다.
- 로컬 행정심판 시스템에는 Telegram 발송 수단이 없다(코드 검색 0건). 로컬 연동기는 30분마다 홈페이지 `GET /api/connector`를 부른다. 하지만 홈페이지는 그 호출 시각을 기록하지 않는다. 그래서 지금은 로컬 PC가 꺼지거나 연동기가 죽어도 아무 신호가 없다.
- 미처리 기준은 연동 계약 `api/_inquiry-contract.json`의 `staleRules`(72시간 지연, 긴급 24시간, 30일 경고, 90일 자동 종결) 한 곳에 있다.
- 긴급 표시는 접수 알림과 같은 기준으로 판정한다(`diagnosis.counts.urgent` 또는 `visaIntake.deadlineFirst`).

## 2. 설계

### 2-1. 어디서 보내나 — 홈페이지 cron (추천)
- 로컬이 아니라 홈페이지(Vercel)에서 보낸다. 로컬 PC가 꺼져도 알림은 오고, 그 알림 안에 "연동기 마지막 접속 n시간 전 ⚠️"가 뜬다. 감시 대상(로컬)이 감시자를 겸하면 꺼졌을 때 아무것도 오지 않는다.
- 새 cron을 만들지 않고 기존 `cron-purge`에 붙인다. 파기를 먼저 하고, 그 결과를 그대로 요약에 넣는다. 그러면 파기 결과를 따로 저장할 필요가 없고, cron 개수도 늘지 않는다.
- 일정은 `0 23 * * *`(UTC)로 바꿔 한국 08시에 돈다. 방침에는 "매일 한 번 자동 점검해 파기"라고만 적혀 있어(`PrivacyPage.tsx:56`) 방침을 고칠 필요가 없다.
- 확인할 것: Vercel Hobby 플랜이면 cron이 지정한 시각의 0~59분 사이 아무 때나 돈다(Vercel 문서 기준). 실제 도착 시각은 배포 뒤에 확인한다.

### 2-2. 연동기 생존 신호(heartbeat)
- `GET /api/connector`가 성공하면 Redis 키 `connector:lastSeenAt`에 현재 시각을 쓴다. 쓰기에 실패해도 GET 응답은 그대로 성공한다.
- 로컬 저장소 코드는 고치지 않는다. 로컬은 지금처럼 GET만 부르면 된다. 운영 연동기에 영향이 없다.
- 판정: 2시간 넘게 접속이 없으면 ⚠️로 표시한다(30분 실행이 4번 연속 빠진 상태). 기록이 아예 없으면 "기록 없음"으로 표시한다(배포 직후).

### 2-3. 요약 내용 (개인정보 없음 — 건수와 접수번호만)
```
[정명 운영 요약] 10/20(화) 08:07 — 확인 필요 1건
· 미처리 2건 (긴급 1 · 지연 1 · 30일 경과 0)
  지연: JM-20261017-AB12 (긴급, 3일째)
· 로컬 미수집 0건 · 진행 중 1건 · 보류 0건
· 연동기 마지막 접속 07:45 (22분 전)
· 자동 파기 오늘 0건 (실패 0)
· 상담 접수: 닫힘(개업 전)
```
- 첫 줄에 "이상 없음" 또는 "확인 필요 n건"을 둔다. n은 접수 단위와 시스템 조건을 더한 값이다.
  - 접수 단위(건마다 1): 지연·30일 경과 건, 2시간 넘게 로컬로 넘어가지 않은 접수, 파기 실패 건. 한 접수가 지연이면서 미수집이어도 한 번만 센다.
  - 시스템 조건(각 1): 연동기 접속 2시간 초과나 기록 없음, 연동기 접속 시각 조회 실패(저장소).
  - 저장소 연결 실패는 별도 경고 메시지로 보낸다.
- 상태 정의(홈페이지 레코드 기준, 파기된 건 제외)
  - 미처리: status `new`. 로컬에서 사건 전환하면 `in_progress`, 종결하면 `done`으로 돌아오므로 양쪽 모두 손대지 않은 건이다.
  - 지연: 접수 후 72시간 경과(긴급은 24시간). 기준 시간에 닿는 순간부터 센다(로컬 `stale_flags`와 같다). 30일 경과는 따로 센다.
  - 로컬 미수집: `pulledAt`이 없는 미완료 건.
- 접수번호는 지연 건 중 오래된 순으로 최대 3개만 적는다. 이름·전화·문의 내용은 넣지 않는다. 접수번호는 이미 접수 알림으로 같은 대화방에 가는 값이다.
- 저장소(Upstash)에 연결하지 못하면 파기와 집계를 건너뛰고 "저장소 연결 실패 ⚠️" 한 줄을 보낸다.
- Telegram 발송이 실패하면 응답 코드 502와 `summarySent:false`를 돌려준다. 요청 제한시간은 10초다. Vercel 로그에만 남는 한계가 있다(알림 수단 자체가 실패한 경우이기 때문이다).

### 2-4. 파일
- 새 파일 `api/_daily-summary.mjs`: 순수 함수 `summarizeInquiries(items, { now })`, `formatDailySummary(summary, ctx)`, `formatStorageFailureSummary(ctx)`. 미처리 기준은 실행 중에 계약 파일을 읽지 않는다. 대신 상수 `STALE_RULES`로 두고, 계약 파일 `staleRules`와 같은지 테스트로 고정했다(배포 때 JSON 파일이 함수에 포함되지 않을 위험을 피하기 위해서다).
- `api/_store.mjs`: `markConnectorSeen(now)`, `getConnectorLastSeen()` 추가.
- `api/connector.js`: GET 성공 뒤 heartbeat 기록(실패 무시).
- `api/cron-purge.js`: 파기 → 집계 → Telegram 발송. 파기·집계·발송을 서로 감싸서 하나가 실패해도 나머지는 진행한다.
- `vercel.json`: 일정만 바꾼다. 이 파일은 CRLF이므로 줄바꿈을 그대로 유지한다.
- 함수 개수는 늘지 않는다(api 함수 6개 그대로).

## 3. 하지 않는 것
- 로컬 사건의 청구기한 임박 알림은 하지 않는다. 기한은 로컬 DB(사건·`deadline_calc`)에만 있다. 이를 보내려면 로컬에 Telegram을 붙이거나 로컬이 건수를 홈페이지로 올려야 한다. ① 수임 사건이 생긴 뒤 별도 과제로 한다.
- 로컬 상태 반영 오류(PATCH 실패)는 홈페이지가 볼 수 없다. heartbeat는 GET 성공만 뜻한다. 그래서 GET은 되고 상태 반영만 실패하는 경우는 이 요약에 잡히지 않는다.
- 자동 고객 발송은 하지 않는다. 이 알림은 사무소 대화방에만 간다.

## 4. 순서 (TDD)
1. `_daily-summary` 테스트를 먼저 쓴다. 미처리·긴급·지연·30일·미수집 분류, 접수번호 3개 제한, 개인정보 미포함, 이상 없음/확인 필요 문구 → RED 확인 → 구현.
2. connector GET heartbeat 테스트(기록, 기록 실패 시에도 200) → 구현.
3. cron 테스트: 파기 뒤 요약 발송, 저장소 오류 시 경고 발송, Telegram 실패 시 502, 기존 파기 테스트 유지 → 구현.
4. 타입 검사, `npx vitest run --exclude ".claude/**"`, 빌드(guard), verify-dist.
5. 리뷰 에이전트 → 보완.
6. 두 저장소 checklist·memory를 갱신하고 커밋한다(홈페이지는 커밋만, 푸시는 승인 뒤).
7. 배포는 주인님 승인 뒤에 한다. 배포 뒤 확인할 것
   - 30분 안에 heartbeat가 기록되는지 확인한다. Vercel 대시보드 Cron Jobs의 Run 버튼으로 한 번 돌려 실제 메시지를 받아 본다. 이때 파기도 함께 돈다(대상이 없으면 0건이고 멱등이다).
   - 다음 날 08시대 도착을 확인한다.
