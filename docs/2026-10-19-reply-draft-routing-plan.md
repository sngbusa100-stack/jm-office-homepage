# ④+⑤ 회신 초안 자동 작성과 6개 분야 처리 경로 — 계획 (2026-10-19, 주인님 승인: 추천안 + 서명에 사무실 이메일)

방향 문서 `docs/2026-10-19-function-direction.md` 5절의 세 번째 순서다. 파이프라인에서 행정사 손이 가장 많이 가는 곳, 곧 "접수 → 첫 회신"을 줄이는 것이 목적이다.

## 1. 현황 (코드 확인 결과)

### 홈페이지 /admin
- "회신문 생성" 버튼이 `src/data/replyTemplates.ts`의 분야별 고정 템플릿에 이름과 접수번호만 채운다(`AdminPage.tsx:154`).
- 고객이 접수 때 이미 답한 것을 쓰지 않는다. 비자 접수 질문 16개와 셀프 진단 답변(4개 분야, 분야마다 9~12문항)을 받아 두고도 같은 것을 다시 묻는다. 예: 비자 템플릿은 "현재 체류자격과 만료일"을 묻는데, 비자 접수 질문에 이미 `currentStatus`·`expiryDate`가 있다. 이것이 GP-05 미반영이다.
- 기한 우선 건(진단 긴급, 비자 `deadlineFirst`)도 일반 건과 같은 순서로 쓴다.
- 인사말에 대표 행정사 이름과 서명이 없다(보고서 BR-15).

### 로컬 대기함 (`admin_appeal/ui_admin.py:193`)
- 분야 → 사건 유형 연결(`store.py:106 TOPIC_CASE_TYPE`)은 음주운전·영업정지 2개뿐이다.
- 나머지 4개 분야(인허가·출입국 비자·국가보훈·토지보상 내용증명 계약서)는 "행정심판 문서 자동화 대상 분야가 아닙니다. 전화·이메일로 직접 회신하세요." 경고만 뜬다. 초안도 없고, '회신했다'는 표시도 없다.
- 그래서 회신을 마친 건도 홈페이지에는 '신규'로 남는다. 아침 운영 요약에서도 72시간이 지나면 '지연'으로 잡힌다. 손댈 방법은 '문의 종결'뿐인데, 그러면 고객 답을 기다리는 중인데도 처리 완료가 되어 120일 파기가 시작된다.

### 분야 목록이 네 곳에 따로 있다
- `api/_validate.mjs TOPICS`
- 상담 화면 분야 선택(ConsultPage)
- `replyTemplates.ts`의 topic
- 로컬 `TOPIC_CASE_TYPE`

라벨 하나를 바꾸면 로컬 라우팅이 조용히 '수동 분류'로 떨어진다(보고서 17번).

## 2. 설계

### 2-1. 회신 초안 엔진은 한 곳에 (추천)
- 새 파일 `api/_reply-draft.mjs`(순수 함수)를 둔다. 템플릿 데이터를 이리로 옮기고 `buildReplyDraft(record, { office })`가 초안을 만든다.
- 홈페이지 /admin은 이 모듈을 그대로 쓴다. 화면 코드가 api 모듈을 가져오는 방식은 이미 쓰고 있다(`src/lib/inquiryContract.ts`가 `api/_store.mjs`를 가져옴).
- 로컬은 연동기가 가져갈 때 초안을 함께 받아 저장한다(2-4). 파이썬으로 같은 로직을 다시 짜지 않는다. 그래서 두 화면의 초안이 늘 같다.
- 클라우드 레코드에는 초안을 저장하지 않는다. GET 응답에서 그때그때 계산한다. 그래서 클라우드에 개인정보 사본이 늘지 않는다.

### 2-2. 초안 작성 규칙 (GP-05)
1. **인사·서명**: "정명 행정사사무소 대표 행정사 정재훈입니다."로 시작하고, 끝에 사무실 전화와 이메일을 붙인다(2026-10-19 주인님 결정). 이름·전화·이메일은 `office.json`에서 가져오고 휴대폰은 넣지 않는다.
2. **기한 우선**: 긴급 건(진단 긴급 또는 비자 `deadlineFirst`)은 인사 바로 다음 줄에 기한 확인을 둔다.
   - 예: "기한이 임박했을 수 있어 먼저 여쭙습니다. 처분 통지서를 받으신 정확한 날짜를 알려 주십시오."
   - 비자 건은 고객이 적은 마감일을 그대로 인용한다.
   - 기한 날짜는 계산하지 않는다. 계산은 로컬 `deadline_calc`의 몫이다. 초안에는 "확인이 필요하다"는 말만 둔다.
3. **이미 받은 답은 다시 묻지 않는다.** 대신 "알려 주신 내용(고객 자가 응답, 확인 전)" 묶음으로 짧게 되짚는다. 예: "혈중알코올농도: 0.08% 이상 ~ 0.1% 미만".
4. **'모름'이나 무응답 문항은 다시 묻는다.** 정확한 날짜가 필요한 질문(통지서 수령일, 만료일)은 진단에서 기간 구간만 받았으면 날짜를 다시 묻는다.
5. **분야별 보강** (보고서 BR-15·GP-05)
   - 영업정지: 사전통지 단계라면 의견제출 기한 확인을 넣는다. 근거 조문(행정절차법 제21조·제27조)은 구현 때 law.go.kr 원문으로 다시 대조한다.
   - 출입국: 질문 순서를 기한 → 한국/해외 → 자격 → 원하는 도움 → 관계 → 기존 신청·안내로 둔다. 질문마다 '모름'을 허용한다. 국적과 위반 이력은 두 번째 회신으로 미룬다. `stayStatus`가 unsure면 한국/해외 질문을 생략하지 않는다.
6. **변하지 않는 원칙**
   - 결과를 예단하거나 약속하지 않는다. 기존 금지어 검사를 초안 문구에도 적용한다.
   - 자동 발송하지 않는다(2026-07-11 결정). 초안 → 행정사 검토·수정 → 행정사가 직접 발송한다.
   - 연락 언어가 한국어가 아니면 초안 맨 위에 "연락 언어: English — 번역 검수 필요"를 표시만 한다. 번역은 하지 않는다.

### 2-3. 6개 분야 처리 경로와 '회신함' 상태
- 분야마다 경로를 하나로 정해 연동 계약 `api/_inquiry-contract.json`에 `topics`로 싣는다.
  - `case`(사건 전환 가능): 음주운전 → driver_license, 영업정지 → business_suspension
  - `reply`(회신 처리): 인허가, 출입국·비자, 국가보훈, 토지보상·내용증명·계약서
- 로컬은 하드코딩된 `TOPIC_CASE_TYPE` 대신 계약 파일을 읽는다. 홈페이지에서 라벨이 바뀌면 계약 테스트가 깨지고, sync로 로컬에 다시 복사해야 한다. 그래서 조용히 '수동 분류'로 떨어지지 않는다.
- 로컬 대기함 화면을 두 묶음으로 나눈다.
  - **사건 전환 대기**: 지금처럼 사건 입력으로 가져오기
  - **회신 대기**: 4개 분야와, 사건 분야지만 아직 회신 전인 건
  - 모든 건에 회신 초안(복사용)과 **'회신함' 버튼**을 둔다.
- '회신함'은 로컬 상태 `replied`로 기록하고 홈페이지에 반영한다.
  - 홈페이지 status `new` → `in_progress`, 단계는 `inquiry`로 둔다.
  - 운영 요약의 '미처리·지연'에서 빠진다. 120일 파기는 시작되지 않는다.
  - 기존 규칙을 그대로 지킨다. 단계는 앞으로만 가고, 처리 완료는 되돌리지 않는다. 이미 진행 중이거나 사건 전환된 건에는 영향이 없다.
  - 회신 뒤 고객이 답하지 않으면 지금처럼 90일 무처리 자동 종결을 적용한다. 다만 회신한 건은 "회신 후 무응답 종결"로 사유를 구분한다.
  - 주의할 충돌이 하나 있다. 지금 홈페이지 규칙은 auto_stale 종결이 '진행 중' 건의 상태를 바꾸지 않게 되어 있다. 관리자가 다루던 건을 보호하기 위한 규칙이다. 그런데 회신한 건은 '진행 중'이 되므로, 그대로 두면 90일 종결이 홈페이지에 반영되지 않는다. 그러면 처리 완료가 되지 않고 120일 파기도 영영 시작되지 않는다. 그래서 새 사유는 "로컬이 replied로 올린 진행 중 건"에 한해 처리 완료로 바꾸게 하고, 테스트로 고정한다.

### 2-4. 연동 (하위 호환)
- connector GET이 각 접수에 `replyDraft`(`{ text, notes } | null`)를 붙여 돌려준다. 계산 오류는 건별 null이다. 예전 로컬 연동기는 이 필드를 무시하므로 영향이 없다.
- connector PATCH `action=status`에 `localStatus: 'replied'`를 추가한다.
  - 홈페이지를 먼저 배포한다.
  - 배포 전에 로컬을 커밋하면 예전 서버가 400으로 거절한다. 그 오류는 기록해 두고 다음 실행에서 재시도된다(지난번과 같은 방식).
  - 로컬은 커밋 즉시 운영에서 돌기 때문에, 로컬 커밋은 홈페이지 배포 뒤에 한다.
- 로컬 대기함에 열 2개를 추가한다(멱등 마이그레이션): `reply_draft`(받은 초안), `replied_at`.
- 이미 가져온 예전 건(지금은 7월 시험 접수 1건뿐)에는 초안이 없다. 화면에는 "초안 없음 — 홈페이지 /admin에서 생성"으로 표시한다.

### 2-5. 구현하면서 정한 것 (2026-10-19)
- 로컬 대기함은 분야가 아니라 처리 상태로 나눴다. **회신 대기**(첫 회신 전)와 **회신함**(고객 답 기다림)이다. 사건 분야(음주운전·영업정지)는 어느 묶음에서든 '사건 입력으로 가져오기'를 쓸 수 있다.
- 버튼 이름은 '회신 완료 기록'이다. "고객에게 회신을 보냈습니다" 확인란을 먼저 선택해야 기록된다. 되돌리는 버튼은 없다.
- 회신 후 무응답 종결은 접수일이 아니라 **회신 시각부터 90일**로 센다. 접수 85일째에 회신했는데 5일 뒤 닫히는 일을 막기 위해서다.
- 고객이 답해 업무가 이어지면 **'고객 응답 받음'**으로 90일을 다시 센다. 회신 분야는 사건 전환 경로가 없어서, 이 버튼이 없으면 진행 중인 건도 무응답으로 닫힌다(로컬 리뷰 P1).
- 회신함 건의 제목에는 '회신 후 N일째 · 자동 종결 예정 날짜'를 표시한다.
- 한계: 로컬 대기함의 종결 건(개인정보·회신 초안)을 파기하는 절차는 아직 없다. 기존부터 있던 과제이며, 로컬 파기를 만들 때 `reply_draft` 열도 포함해야 한다.

## 3. 하지 않는 것
- 고객에게 자동 발송(이메일·문자)
- 번역, 다국어 초안
- LLM 생성. 초안은 규칙과 템플릿으로만 만든다(로컬 CLAUDE.md 9번: 숫자·조문은 LLM에 묻지 않음)
- 기한 날짜 계산. 로컬 사건 등록 뒤 `deadline_calc`가 맡는다
- 사건 유형 추가. 인허가·보훈 등을 행정심판 사건 유형으로 만들지 않는다. 업무 범위와 법적 한계 때문이다(행정사의 행정심판 대리 불가)

## 4. 순서 (TDD, 저장소별)

### 1단계: 홈페이지 — 먼저 배포
1. `_reply-draft` 테스트를 쓴다(RED → 구현).
   - 분야별 기본 초안
   - 이미 받은 답 생략과 되짚기, '모름' 재질문
   - 긴급 첫 줄
   - 출입국 순서, 국적·위반 이력 제외
   - 서명, 금지어 검사, 개인정보는 이름과 접수번호만
2. /admin을 새 엔진으로 바꾼다. 기존 `replyTemplates.ts`는 제거하거나 재노출한다(관리자 화면 테스트 갱신).
3. 연동 계약에 `topics`(경로)와 `replied`를 추가한다. `applyConnectorStatus` 규칙과 테스트, connector GET `replyDraft`, 계약 재생성까지 한다.
4. 타입 검사, 전체 테스트, 빌드, verify-dist를 돌린다.
5. 분야별 초안 예시 6개를 주인님께 보여 드리고 문구 확인을 받는다.

### 2단계: 로컬
6. 계약 사본을 sync하고, 라우팅을 계약 기준으로 바꾼다(테스트).
7. 열 추가, `reply_draft` 저장, '회신함' 기록과 상태 반영, 자동 종결 사유를 구분한다(테스트).
8. 대기함 화면을 두 묶음으로 나누고 초안·버튼을 단다.
9. 왕복 실측을 한다. 실제 핸들러는 `scripts/dev-connector-server.mjs`로 띄우고, 로컬 연동기는 `--db 임시경로`로 돌린다. 운영 DB는 쓰지 않는다.

### 3단계
10. 리뷰 에이전트 → 보완
11. 두 저장소 checklist·memory 갱신
12. 배포는 주인님 승인 뒤에 한다. 홈페이지 배포 → 운영 확인 → 로컬 커밋(이때 운영 반영) 순서다.

작업량은 M~L이다. 지난 ①+②와 비슷한 규모로, 두 저장소를 함께 고친다.

## 5. 주인님께 여쭐 것
1. **'회신함' 상태를 추가할까요? (추천)** 추가하지 않으면 회신한 건이 계속 '신규·지연'으로 남습니다. 그러면 아침 요약이 매일 경고를 보내게 됩니다.
2. **서명 문구**: "정명 행정사사무소 대표 행정사 정재훈" + 사무실 전화로 할까요(추천)? 이메일도 넣을지 정해 주십시오.
3. **초안을 보여 드리는 시점**: 1단계 5번(홈페이지 구현 직후, 배포 전)에 분야별 예시 6개를 먼저 확인받는 방식(추천)으로 할까요?
